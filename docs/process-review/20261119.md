## 建議（依效益排序）
1. **封存已完成的內容，讓 pm 必讀檔降到各 ≤ 20KB**。把 work-plan／backlog／status 內已合併的批次與任務移到 `projects/teacher-crm/archive/`（原樣保留），主檔只留進行中與待辦。預期：pm 呼叫的讀檔量減少約 70%，工具呼叫降到 ≤ 20。怎麼量：三檔 `wc -c`、下次 pm 的「工具呼叫」。風險：歷史查找多一步；回退＝把檔案搬回。不碰界線。
2. **子代理回報限 15 行、細節寫進交接檔**。回覆只放：結論、verdict／status、關鍵數字、需要使用者決定的事、交接檔路徑；實測輸出、檔案清單、假設全部寫進 `tasks/<任務>/*-notes.md`（調度者要時再讀）。預期：調度者 context 成長速度約降一半。怎麼量：同一類任務結束時調度者 context 的增量。風險：低；回退＝刪一行規則。改動處：協議第 8 節＋`/dispatch` 的 prompt 範本一行。
3. **縮減完整路線的任務清單顆粒度（需使用者決定，因屬專案自有的 skills 流程）**。現在每個測試切片展開成紅／綠／重構三個任務。改成「每個切片一個任務，內含先紅後綠與重構步驟」，任務數約降為 1/3，tasks.md 約從 84KB 降到 30KB 以下。TDD 紀律由 engineer-rules 與 QA 的「破壞實測」把關，不靠任務數量。預期：/tasks 階段約省 10 萬 token／任務，工程師每輪少讀約 5 萬。怎麼量：tasks.md 大小、pm 該階段 token。風險：任務粒度粗，工程師中斷時的接續點較少（可用「切片」作為接續點）；回退＝用原 skill 重跑。小任務可直接走快速路線，不受影響。
4. **避免重複調度**。`bin/console ui` 為已有進行中任務（worktree 有未提交變更或 tasks 有交接檔）的卡片隱藏或警告「建立對話」；已建立的 dev-* 閒置 session 各佔 6～25 萬 context，使用者不需要時可關閉。預期：不再發生互蓋與重工。怎麼量：同一任務同時有兩位調度者的次數（目標 0）。風險：低。需要改 `ui.py`（有測試）。
5. **額度感知並行度**：每週額度 ≥ 80% 時，同時進行的完整路線任務上限降為 2，並優先收尾（驗收、合併）而不是開新線。預期：減少被保護機制擋下的空等。怎麼量：額度保護觸發次數與等待時間。風險：吞吐量降低但不會停擺。

## 補充發現（2026-11-19，採用 2、1、3 之後）
8. **自動派工空轉，是最大一筆浪費**：21 個 `dev-teacher-crm-*` session（自動派工每次啟動的 `/dispatch --auto`）、work-plan 有 17 處「沒有可挑」；其中 7 個 session 近 24 小時約 187 萬 token。原因：`ready_items` 只看「待辦且無待決」，專案管理員還會排除依賴未合併、檔案衝突、model 通道，所以挑不出來、狀態不變，冷卻後又啟動。設定檔為 `enabled: true`。**已處理（2026-11-19）**：使用者選擇先停用再修；自動派工新增「局面指紋」，局面沒變就不再派（`autodispatch.fingerprint`，`tests/test_autodispatch.py` 新增 8 個測試）。量測：重新啟用後 `runtime/auto-dispatch.log` 的派工次數與 `work-plan.md`「沒有可挑」的新增筆數（基線：24 小時 21 個 session）。
9. **code map 有在用**：92 份子代理逐字稿中 38 份讀過；engineer-rules 第 4 節已要求。它只有 17KB，原始碼不是大頭，大頭是規格文件與管理檔。
