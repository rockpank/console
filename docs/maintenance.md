# 維護注意（細節）

> 2026-11-17：Redmine 工單時代的條目已移到 `legacy/redmine/docs/maintenance-legacy.md`，這裡只留現行模組。`CLAUDE.md` 只留會影響日常操作的硬規則。

- 測試：`python3 -m unittest discover -s tests`（不碰真實 docker、tmux、網路；git 用暫存 repo）。改 `mask.py`／`usage.py`／`ui.py`／`site.py`／`worktree.py` 後一定要跑。Redmine 時代的測試在 `legacy/redmine/python/tests/`，不在這條跑。
- 遮蔽（`mask.py`）有兩類：祕密（金鑰、密碼、token、私鑰、連線字串帳密 → `[SECRET]`，`_SECRET_RULES`，最先處理）與個資。`detect()`／`scan` 與 `mask_text()` 用同一套規則，「命中」＝「真的會被換掉」。「名稱=值」只遮值，且略過變數、函式呼叫、`Token::CONST`、路徑、佔位符與 `dummy-`／`fake-`／`example-`／`test`／`demo` 開頭的假值，以免掃描誤判把流程卡在「有疑似」；調整規則後用 `tests/test_mask_secrets.py` 的 `NotSecretTests` 守住誤判。**客戶資料遮蔽不得放寬**（組織規定）。讀取階段不因客戶資料停下：未讀的二進位附件、疑似未遮蔽名稱只是提醒，單一附件下載失敗會略過（見協議「不因客戶資料而中斷」）。
- 用量監控（`bin/console usage [--json] [--check]`、介面上方的「用量監控」面板，`usage.py`）：達 `[usage] alert_percent`（預設 90）就告警——介面橫幅＋標題加 ⚠＋桌面通知（按「開啟桌面通知」授權）、`--check` 回傳 1。**額度百分比的唯一可靠來源是 statusline 快照**：`.claude/settings.json` 的 `statusLine` 指向 `bin/usage-statusline`，Claude Code 每次回覆都會餵它 `rate_limits.five_hour/seven_day` 與 `context_window`，它只挑數字寫成 `runtime/usage/<session>.json`（0600，不存路徑與內容，不載入 `console.env`，任何錯誤都靜默結束）；只有 Pro/Max 訂閱、且第一次 API 回應之後才有。沒快照時才用 `[usage]` 的 `five_hour_tokens`／`weekly_tokens` 估算（都是 0＝不估算）。紀錄來源是 `~/.claude/projects/**/*.jsonl`（含 `<session>/subagents/`）：**只抽 usage 數字、時間、sessionId、模型、`dev-` 開頭的對話名稱（任務代號），不讀不存對話內容**（別的對話標題可能含工單內容，一律不顯示）；除錯時也不要把原始行印出來。三個容易踩的點，改動時先看 `tests/test_usage.py`：①同一則回覆的 usage 會重複寫入，必須用 (requestId, message.id) 去重，否則多算約 2 倍；②限流事件（`quotaLimits`）那行本身也是 `type: assistant` 且帶 `usage`，判斷不能用 `elif` 接在用量後面；③context 上限猜錯會天天誤報（實際是 1M 卻當 200k），所以沒有快照也沒在 config 明確設定時，只顯示進度條並標「推測」、**不做 context 告警**。5 小時視窗的重置時間無快照時是照 ccusage 的方式推算（第一則訊息的整點起算，滿 5 小時或中斷 5 小時換新的一塊）。`bin/console ui` 啟動時會在背景先讀一遍紀錄（第一次約 2 秒、之後每次更新數毫秒）。前端沒有單元測試：可用 Windows 端的 `msedge.exe --headless=new --dump-dom／--screenshot` 實際載入頁面檢查（不會開視窗）。
  - **快照要用「數據時間」挑最新的（2026-11-16 修正）**：statusline 的 `rate_limits` 永遠是該對話「最後一次 API 回應」時的值，閒置對話在快取過期等事件重跑時會把舊值（例如 14:05 的 100%、16:20 重置）寫成新快照，用寫入時間排序會讓面板在 30%／100% 間亂跳。所以 `summarize` 的 `data_at(snap) = min(快照寫入時間, 該對話最後一次回應時間)`，`_window` 依它挑；額度卡片顯示「數據 N 分鐘前」，超過 15 分鐘標「可能已過時」。估算的 token 數與「目前 5 小時視窗」也改成跟著快照的 `resets_at`（視窗＝`resets_at − 5h … resets_at`、每週＝`resets_at − 7d`），沒有快照才用紀錄推算（ccusage 式，可能差好幾個小時）。context 的快照只要是在該對話最後一次回應「之後」寫的就有效（閒置多久都一樣）。限流事件是否「已恢復」也用數據時間判斷（事件後有更新的數據顯示該視窗沒滿或換了視窗）。快照清理看檔案 mtime，要用真實時鐘比，不能用快照內的時間（測試用假時鐘時會把剛寫的檔刪掉）。
  - **額度保護**（定義在協議「額度保護」一處）：`usage.guard()` 只看 5 小時／每週額度與進行中的限流（單一對話的 context 告警不算）；`bin/console usage --guard` 結束碼 3＝暫停、0＝可繼續。強制點：`ui.launch`（`HEAVY_ACTIONS`＝dispatch、resume，輸入錯誤優先於額度錯誤）與 `ui.launch_batch`（整批拒絕），`chat`、關閉、移除、擱置、開視窗不受影響；`/dispatch` 在 2a／2c／2d／階段 3／階段 4 每輪／階段 5 修正開始前檢查，暫停時寫 `escalation.md`（`kind: 額度保護`）並 `--set 已升級`，不推播。解除只有 `POST /api/guard`（介面按鈕；要 token；寫 `runtime/usage-guard.json`，0600，最久 5 小時、額度重置即失效，只有達門檻時才能解除）——不要新增讓角色能解除的指令。`ui._guard` 算不出來就放行（fail-open）。`tests/test_ui.py` 的 `UiBase` 預設把 `ui._guard` mock 成未暫停，別讓測試讀真實用量。
- 建 worktree 前先檢查任務是否處理過（`worktree.check_prior`）：本機或遠端已有同名分支（`<branch_prefix><任務>`）就直接用該分支（遠端才有則建本機追蹤分支），**不從起點另開同名分支**。遠端有沒有該分支用 `ls-remote` 確認，連線失敗視為錯誤而不是「沒處理過」；本機落後或與遠端分岔只警告，不合併、不 reset。**不要用 `git log` 抓提交主旨**（可能夾帶客戶名稱）。`env_files` 的 `set` 值原樣覆寫同名鍵（已不做 `{site_url}` 代換）。測試見 `tests/test_worktree.py`（暫存 git repo）。Redmine 時代的 `prior-<專案>.json` 本輪起點標記已移到 legacy。
- 介面（`bin/console ui`，`ui.py`＋`templates/ui/dashboard.html`；2026-11-17 改版，移除 Redmine）：只綁 127.0.0.1，網址帶隨機 token（每次啟動不同），**不自動開瀏覽器**（WSL 下 `explorer.exe <網址>` 會跳出檔案總管），只印網址。單位是「專案＋任務」，資料全部唯讀取自專案工作區：`projects/<專案>/backlog.md`（`parse_backlog` 讀第一張含「ID」「狀態」欄的表）、`tasks/<任務>/` 的交接檔檔頭（欄位見協議第 2 節）、`worktrees/<任務>/<專案>/` 是否存在；階段取 backlog 狀態與交接檔推斷中較後面的（PM 更新可能落後），`完成` 只認 backlog。進行中的條件：backlog 標規劃中／開發中／資安／QA，或已有交接檔／worktree，其餘 backlog 項目只出現在「派工」清單。擱置／排序／已移除存 `runtime/queue.json`（`tasks`／`order`／`removed`，以任務代號為鍵，載入時用 `parse_task` 過濾），**不寫專案文件**。建立對話（`ui.launch`）只在背景開 tmux session `dev-<任務>` 並啟動 `claude`，**不開任何視窗**；已有 session 就不重送指令。「派工」（`ui.launch_batch`，`POST /api/launch-batch`）為勾選的 backlog 項目或一段新需求開**一個** `/dispatch <專案> <ID,ID…>` 對話（session `dev-<專案>-b<HHMMSS>`，一次最多 10 項、先全驗證再動手、新需求先過遮蔽壓成單行限 300 字），切分批次由專案管理員做。卡片動作只有 dispatch／resume／chat 三種（`HEAVY_ACTIONS`＝dispatch、resume），指令只由 `ui.build_prompt` 依白名單組，自由文字只有「裁示」與「新需求」。要互動時按「開指令視窗」（`POST /api/terminal` → `ui.open_window`，只接上既有對話、不建立，才用 `wt.exe`）。「關閉對話」只能關現存的 `dev-` 對話；「移除」＝關閉對話＋從看板隱藏（記下當時的交接檔最新時間，之後有更新或重新派工就自動回來），**不刪 worktree、分支、交接檔**，要清 worktree 走 `bin/console wt rm`。孤兒對話（不是已知任務、也不是批次對話）在警示列有關閉鈕。新增動作時改 `build_prompt`、`launch`、`_actions` 並補 `tests/test_ui.py`。前端沒有單元測試：可用 headless Chrome（`--headless=new --screenshot`）對暫存工作區的假資料實際載入檢查；`wt.exe` 分頁的實機行為沒覆蓋。
- 預覽站 driver：只有 `command`（通用，`site.py`）；cake73（CakePHP + Apache vhost）已移到 `legacy/redmine/python/console_cli/site_cake73.py`，sites.json 裡舊 driver 的紀錄也已移到 `legacy/redmine/runtime/`。`command` driver 的細節與踩過的坑：①指令是字串陣列、不經 shell，占位符只代入白名單內的 6 個，其他 `{…}`／`${…}` 原樣保留；②`run(..., env=)` 把額外環境變數疊在目前環境上，dry-run 會印出（所以不能放祕密）；③`wait_healthy` 的 `fetch` 預設要在呼叫時才取（參數預設值在定義時綁定，測試換不掉 `_fetch`）；④只在「完全沒回應」時重試，500 也是回應、立刻判定失敗；⑤`_fetch` 不跟隨轉址（302 到登入頁就代表活著）；⑥再次 `site add` 會先 stop 再 start、沿用同一個埠；⑦`docker compose run -d` 的一次性容器要用 `--name {name}-web` 才能被 `docker rm -f` 精準移除（compose 2.13 的 `down` 不一定清得掉）；⑧每個任務各 build 一個 `<專案名>-app` 映像檔，`purge` 要 `docker rmi` 掉。看板只接受 `http://localhost|127.0.0.1:<埠>` 的網址當預覽站連結（`ui._site_url`）。測試：`tests/test_site.py`（全程 mock，不碰 docker）。
